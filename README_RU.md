# Проверка сервера для VPN и сетевого трафика

Утилита `server_audit.py` проверяет Windows-компьютер или Linux VPS до ввода сервера в
эксплуатацию. Это самостоятельный файл на стандартной библиотеке Python: бот, база данных,
`.env` и Python-пакеты основного проекта ему не нужны.

## Быстрый запуск

На каждом проверяемом VPS:

```bash
python3 server_audit.py
```

### Установка в Linux как команда `multitest`

Передайте на сервер всю папку `server-audit`, затем запустите установщик:

```bash
cd server-audit
sudo sh install.sh
multitest
```

Установщик копирует самостоятельный Python-файл в `/usr/local/lib/multitest/`, создаёт
команду `/usr/local/bin/multitest` и устанавливает нужные системные программы. Python-пакеты
через `pip` не используются. Поддерживаются `apt`, `dnf`, `yum`, `apk` и `pacman`.
Если зависимости уже установлены или вы хотите управлять ими самостоятельно:

```bash
sudo sh install.sh --skip-deps
```

После публикации на GitHub папку можно устанавливать одной строкой:

```bash
git clone --depth 1 https://github.com/SirScroogee/vpn-server-multitest.git /tmp/multitest-install && sudo sh /tmp/multitest-install/install.sh
```

Проще запустить установщик прямо через `curl`, без клонирования:

```bash
curl -fsSL https://raw.githubusercontent.com/SirScroogee/vpn-server-multitest/main/install.sh | sudo sh
```

После любого из этих вариантов для открытия меню достаточно команды:

```bash
multitest
```

### Локальный запуск из текущего проекта на Windows

В PowerShell из корня проекта:

```powershell
python .\server-audit\server_audit.py
```

Для первого короткого локального прогона без дополнительных Linux-утилит:

```powershell
python .\server-audit\server_audit.py `
  --tests ping,tcp,ipinfo,access,dnscheck `
  --label local-windows `
  --target 1.1.1.1 `
  --target dns.google
```

Windows поддержан для предварительного локального замера: используются системные `ping`
и `tracert`, работают TCP/DNS, Path MTU, IP/гео, сервисы, DPI-профиль и проверки
обычного/защищённого DNS. Инвентаризация
Linux (`vmstat`, `sysctl`, `ip`, `ss`, MTR) на Windows будет пропущена. Полную оценку
кандидатного VPS нужно запускать на самом Linux-сервере.

Если VPS не отвечает на ping, это может быть фильтрация ICMP. Проверьте также порт,
который точно должен быть открыт: `--tests ping,tcp --tcp-port 22` для SSH или
`--tcp-port 443` для HTTPS. Закрытый порт сам по себе не означает, что весь VPS недоступен.

Посмотреть описание каждого теста и текущий каталог публичных точек:

```powershell
python .\server-audit\server_audit.py --explain-tests
python .\server-audit\server_audit.py --list-iperf-servers
```

Выберите один или несколько пунктов меню через запятую. Для первого прогона лучше пункт
`1` — полный тест. После проверки файлы автоматически не создаются. Если результат нужен,
выберите действие `2 — сохранить подробный отчёт в TXT`; файл появится в
`server-audit-reports/`. JSON при обычной интерактивной проверке не создаётся.

Главное меню разделено на смысловые категории: комплексные проверки, сеть и маршрут,
скорость и качество канала, железо и система, IP/сервисы/репутация, справка и настройка.
Нумерация идёт последовательно сверху вниз; по-прежнему можно выбрать несколько пунктов
из разных категорий через запятую. Заголовок каждой категории выделяется ярко-зелёным
жирным текстом; `--no-color` и `NO_COLOR` отключают это оформление вместе с остальными цветами.

Обычный экран намеренно не показывает команды, JSON-метрики и сырой ответ утилит. Вместо
этого у каждой проверки есть свой короткий итог: что измерено, хорошо ли это и что делать
при предупреждении. Технические подробности попадут в TXT только по вашему запросу.
После любого интерактивного теста программа не закрывается и предлагает:

```text
1 — вернуться в главное меню
2 — сохранить подробный отчёт в TXT
3 — повторить эту же проверку
0 — выйти
```

При первом запуске, возврате в главное меню, открытии справки пункта 17 и показе готового интерактивного отчёта
консоль очищается. Поэтому предыдущие команды, старый прогресс и прошлый результат не
смешиваются с новым экраном. При неинтерактивном запуске с `--tests` очистка отключена,
чтобы не портить перенаправленные логи и историю терминала.

Каждая проверка спрашивает только то, что использует:

- IP — текущий IP или конкретный адрес;
- ping/MTR/traceroute/Path MTU — адрес назначения;
- TCP/UDP-порт — адрес и один номер порта для обоих протоколов;
- `iperf3 TCP` — желаемую скорость, число параллельных потоков и публичную/собственную `iperf3`-точку;
- `iperf3 UDP` — собственную `iperf3`-точку и размер UDP-потока;
- длительный тест — цель, порт, длительность и, только по желанию, собственную iperf3-точку;
- система, диск, сервисы, DPI и DNS-резолверы — никаких дополнительных параметров.

Метка больше не запрашивается: она автоматически создаётся по локальной дате и времени,
например `audit_130826_1927`. При ручном сохранении эта же строка становится именем `.txt`-отчёта.
Если два запуска завершатся в одну минуту, второй получит суффикс `_2`, поэтому существующий
отчёт не будет перезаписан. При необходимости своё название всё ещё можно передать через
`--label msk-provider-a`; на измерения и итоговый балл оно не влияет.

Во время запуска показывается общий progress bar: процент, примерное оставшееся время и
название текущего этапа. ETA уточняется после каждого завершённого теста и остаётся
оценочным, поскольку сетевые тайм-ауты и занятость публичного `iperf3` заранее неизвестны.
Для перенаправления вывода в машинный лог индикатор можно отключить через `--no-progress`.

В интерактивном терминале понятный отчёт использует цвета: зелёный — успешная проверка,
жёлтый — предупреждение/неполный результат, красный — подтверждённая проблема или ошибка.
Цветовые коды не записываются в TXT. Цвет можно отключить через `--no-color` или
стандартную переменную окружения `NO_COLOR`.

Начиная с версии 1.9 результаты построены вокруг главной метрики выбранного теста. Сразу под крупным
итогом показываются значения с маркером `◆`: IP/провайдер/ASN/геолокация, RTT и потери,
upload/download, Path MTU, доступность сервисов, скорость диска либо CPU/RAM/steal.
Результаты разделены тонкими линиями, а служебные блоки вроде «Что получилось» и
«Что случилось» удалены. Символы `✓`, `!`, `✗` и цвет позволяют быстро отличить норму,
предупреждение и проблему; строка `→` обозначает рекомендуемое следующее действие.

Сайты и российский DPI-профиль показываются таблицей `СЕРВИС / IP / HTTP / HTTPS`:
видны фактический IPv4, код ответа и адрес перенаправления. DNS показывается таблицей
`RESOLVER / IP / UDP/53 / TCP/53 / DoH/443 / DoT/853` для двух адресов каждого из
Cloudflare, Google, Quad9 и Yandex. MTR выводит таблицу потерь и задержек каждого хопа.
Traceroute тоже показывает полный маршрут таблицей `ХОП / УЗЕЛ или IP / RTT 1 / RTT 2 /
RTT 3 / СТАТУС`: Windows-задержки, Linux traceroute, частичные ответы и тайм-ауты разбираются
по отдельным колонкам. Открывать TXT ради маршрута не требуется. Длинные значения аккуратно
сокращаются под ширину терминала.

В версии 1.10 таблицы также используются там, где нужно сравнивать однотипные числа. Короткий
тест диска показывает `ОПЕРАЦИЯ / ОБЪЁМ / СКОРОСТЬ / СТАТУС`; чтение помечено как справочное,
поскольку его может ускорять системный кэш. Ping, TCP-порт, iperf3 TCP/UDP и системные ресурсы
тоже выводятся по именованным колонкам. При нескольких целях или iperf3-точках заголовок
печатается один раз, а каждая цель занимает отдельную строку. Одиночные результаты вроде
Path MTU и подробные текстовые выводы IP-баз оставлены без искусственно широкой таблицы.

В версии 1.13 пункт 6 проверяет выбранный порт по TCP и UDP и показывает протоколы
отдельными строками. Для UDP молчание честно обозначается как `open|filtered`: оно не
доказывает ни открытый, ни закрытый порт. Пункт 10 проводит пятиминутное наблюдение за
ping и TCP; с собственной iperf3-точкой он одновременно создаёт длительную нагрузку,
сравнивает интервалы скорости и ищет burst-лимит. Пункт 17 очищает консоль перед справкой.

Пояснения под результатами теперь контекстные. Например, справка про HTTP 403 появляется
только при фактическом ответе 403/451, предупреждение о тайм-ауте — только при отсутствии
соединения, а оговорки про DPI, DNS, MTR и traceroute — только когда измерение действительно
содержит соответствующую аномалию. Перед такими подсказками выводится отдельный разделитель.

## Одна обычная проверка сервера

Режимы `node`, `bridge` и `universal` удалены из меню и отчёта. Теперь используется один
сбалансированный профиль оценки сервера для VPN и обычного сетевого трафика: задержка 30%,
стабильность 25%, пропускная способность 35%, система 10%. Набор измерений выбирается
пунктами меню, а не абстрактной ролью. Старый параметр `--role` скрыто принимается только
для совместимости и ни на что не влияет.

Если сервер будет частью цепочки, просто добавьте адрес второго сервера как обычную цель
для ping/MTR и используйте его как собственную точку `iperf3`. Отдельный режим для этого
не нужен.

Перед каждой проверкой скрипт автоматически смотрит только те внешние программы, которые
нужны выбранным тестам. Если всё установлено, отдельное сообщение не показывается. Если
чего-то нет, в итоговом экране появляется таблица с названием программы, зависимым тестом
и последствием: весь тест будет пропущен либо не появится только дополнительная метрика.
Остальные проверки продолжают работать.

Пример установки полного набора Linux-утилит для Debian/Ubuntu:

```bash
sudo apt-get update
sudo apt-get install -y iputils-ping mtr-tiny traceroute iperf3 openssl procps iproute2
```

Сам `server_audit.py` ничего не устанавливает и системные настройки не меняет. Системные
пакеты устанавливаются только при явном запуске `sudo sh install.sh`; параметр
`--skip-deps` отключает даже это. При обычном запуске `multitest` недостающие программы
по-прежнему только перечисляются вместе с готовой командой установки.

Пункт «Что означает каждый тест» теперь показывает справку таблицей `ТЕСТ / ЗНАЧЕНИЕ`.
Длинный текст переносится внутри своей строки, а тесты разделены линиями, поэтому описание
не сливается в один блок.

## Правильная схема измерений

Сетевой тест всегда характеризует конкретный маршрут, направление и момент времени.
Ping с VPS до `1.1.1.1` не показывает задержку будущего российского пользователя до
этого VPS.

Для VPN-сервера нужны два вида замеров:

1. С домашней/мобильной сети пользователя — до публичного IP кандидатной ноды.
2. С кандидатной ноды — до нужных сайтов, DNS и своей контрольной `iperf3`-точки.

Для цепочки из нескольких серверов укажите IP следующего сервера как `--target`, а
`iperf3` запустите непосредственно между этой парой. Итог ограничивает самый медленный
участок, а задержки участков складываются.

### «Цель» и iperf3-сервер — разные вещи

Обычная цель (`--target`) нужна только тестам `ping`, MTR, traceroute, Path MTU и
DNS/TCP. Она отвечает на вопрос: «какая задержка, маршрут и доступность от машины, где
запущен скрипт, до этого адреса?» При выборе только `iperf3` скрипт больше не спрашивает
такую цель.

Сам `iperf3` всегда требует две стороны:

1. На проверяемой машине работает клиент `iperf3 -c`.
2. На другой машине должен работать сервер `iperf3 -s`.

Поэтому IP/hostname второй стороны необходим самому протоколу `iperf3`: клиент должен
знать, куда отправлять тестовый поток. В скрипте эта сторона выбирается отдельно — из
публичного российского каталога или через `--iperf-server host:port`. Это не IP
проверяемой машины, если скрипт уже запущен на ней.

При обычном запуске выполняются два самостоятельных замера:

- upload: проверяемая машина отправляет данные на iperf3-сервер;
- download: сервер отправляет данные обратно с помощью reverse-режима `-R`.

Каждое направление по умолчанию работает 10 секунд, первые 2 секунды исключаются как
разогрев (`-O 2`), а результат читается из JSON. TCP запускается с четырьмя параллельными
потоками (`-P 4`); число теперь спрашивается в меню и меняется параметром
`--iperf-streams`. Несколько потоков нужны, чтобы один TCP flow с небольшим окном или
одним перегруженным ядром не занизил доступную пропускную способность маршрута. При этом
слишком много потоков тоже может искусственно загрузить CPU, поэтому обычный ориентир — 4.

В таблице показываются точка, направление, число потоков, суммарная скорость и TCP-повторы.
TCP-повтор означает, что сегмент пришлось отправить снова из-за потери или отсутствия
подтверждения. Ноль — хороший признак, но универсального порога нет: число зависит от
длительности и объёма. Поэтому скрипт дополнительно показывает повторы на переданный ГиБ.

Если скрипт запущен на локальном ПК, результат характеризует маршрут `ПК ↔ публичная
iperf3-точка` и практически ничего не говорит о ещё не приобретённом VPS. Если скрипт
запущен внутри тестируемого VPS, результат уже характеризует `VPS ↔ публичная точка`.
Для пары собственных серверов наиболее полезно запустить `iperf3 -s` на втором сервере
и тестировать именно маршрут между ними.

## iperf3 без случайных публичных серверов

### Публичные серверы в России

В интерактивном меню при выборе TCP `iperf3` предлагаются:

- обзор РФ: Москва, Санкт-Петербург, Екатеринбург, Новосибирск и Краснодар;
- запад/юг России;
- Урал/Поволжье;
- Сибирь/Дальний Восток;
- ручной выбор одного или нескольких городов;
- собственный endpoint.

Каталог загружается из проекта
[`itdoginfo/russian-iperf3-servers`](https://github.com/itdoginfo/russian-iperf3-servers),
который ежедневно проверяет доступность российских точек. Если GitHub недоступен,
используется встроенный резервный список из 16 endpoint нескольких операторов и регионов.
Перед нагрузкой утилита перебирает заявленные порты и коротким `iperf3`-запросом ищет
реально работающий и не занятый порт.

Неинтерактивный обзор РФ:

```bash
python3 server_audit.py --tests iperf --iperf-profile ru-core
```

Конкретные города:

```bash
python3 server_audit.py \
  --tests iperf \
  --iperf-city Moscow \
  --iperf-city Yekaterinburg \
  --iperf-city Novosibirsk
```

Профили: `ru-core`, `ru-west`, `ru-ural-volga`, `ru-siberia-east`. Публичные серверы
дают полезное сравнение маршрутов по РФ, но не являются эталоном канала: точка может быть
нагружена другими тестами. Слабый результат следует повторить и подтвердить на собственной
контрольной машине.

UDP на этих публичных точках автоматически не запускается, поскольку ежедневный каталог
подтверждает TCP `iperf3`, но не разрешение владельцев на UDP-нагрузку.

### Собственный сервер

На своей контрольной машине установите `iperf3`, разрешите TCP и UDP порт 5201 в
firewall только для IP тестируемого VPS и запустите:

```bash
iperf3 -s
```

На кандидате используйте пункт 8 либо команду:

```bash
python3 server_audit.py \
  --tests full \
  --label de-provider-a \
  --target 203.0.113.20 \
  --iperf-server 203.0.113.20:5201 \
  --expected-mbps 500 \
  --udp-mbps 100
```

Адреса `203.0.113.20` в примере замените реальным адресом вашей контрольной точки.

Длительная проверка без нагрузки запускается пунктом 10. Чтобы теми же пятью минутами
проверить ещё и burst-лимит скорости, укажите только собственный сервер:

```bash
python3 server_audit.py \
  --tests soak \
  --target 1.1.1.1 \
  --tcp-port 443 \
  --soak-seconds 300 \
  --soak-iperf-server 203.0.113.20:5201 \
  --iperf-streams 4 \
  --expected-mbps 500
```

Публичные iperf3-точки для этого режима намеренно не используются: пятиминутный поток
занял бы общий сервер для других людей и исказил бы результат из-за их параллельной нагрузки.

TCP проверяется в обе стороны четырьмя потоками по умолчанию. UDP тоже проверяется в обе стороны, но
заданный bitrate должен быть ниже уже известной пропускной способности канала. Иначе
тест сам создаст потери и вывод будет бесполезен.

После теста остановите `iperf3` и закройте порт, если он больше не нужен.

На Windows ESnet официально не поддерживает `iperf3`; существуют сторонние Cygwin-сборки.
Предпочтительный локальный вариант — WSL с Ubuntu:

```powershell
wsl --install -d Ubuntu
wsl sudo apt-get update
wsl sudo apt-get install -y python3 iputils-ping mtr-tiny traceroute iperf3 openssl procps iproute2
wsl python3 /mnt/c/Users/scroo/PyCharm/vpn-bot/server-audit/server_audit.py
```

Если отчёт пишет `Команда iperf3 не установлена`, тест скорости вообще не запускался:
это не нулевая скорость и не отказ публичного сервера. На Linux/VPS установите утилиту:

```bash
sudo apt-get update && sudo apt-get install -y iperf3
```

На Windows рекомендуется установить WSL из PowerShell от администратора командой
`wsl --install -d Ubuntu`, перезагрузиться, установить `iperf3` внутри Ubuntu и запускать
весь `server_audit.py` внутри WSL. Официальный проект ESnet не поддерживает Windows как
основную платформу `iperf3`, поэтому случайная сторонняя Windows-сборка хуже подходит для
сопоставимых тестов будущих Linux VPS.

## Что именно проверяется

- `ping`: RTT, потери и mdev (в отчёте назван jitter/разбросом);
- `MTR`: маршрут и таблица статистики всех хопов прямо в консоли;
- TCP `traceroute` на порт 443: полный маршрут со всеми хопами прямо в консоли в виде
  подписанной таблицы; на Windows используется системный ICMP `tracert`;
- проверка порта: пять TCP-подключений и три UDP-пробы; UDP-ответ подтверждает сервис,
  ICMP-отказ подтверждает закрытие/недоступность, молчание остаётся неопределённым;
- `iperf3 TCP`: upload/download, число параллельных streams, скорость, загрузка CPU,
  TCP retransmissions и нормализованные повторы на ГиБ;
- `iperf3 UDP`: фактический bitrate, потери и jitter;
- длительный тест: в течение 300 секунд интервалы ping, RTT/p95, всплески задержки,
  TCP-доступность и полные обрывы. Только со своей iperf3-точкой добавляются длительная
  многопоточная скорость, минимум/максимум интервалов, разброс, падение к концу и TCP-повторы;
- Path MTU: максимальный IPv4 ICMP-пакет с DF без фрагментации. Он убран из `quick`
  и `full`, не влияет на балл и оставлен отдельным пунктом только для диагностики
  зависаний/неправильного MTU уже настроенного VPN;
- DNS и TCP handshake на 443;
- Cloudflare, Google, Quad9 и Yandex: обычный DNS по UDP/53 и TCP/53, защищённый
  DNS-over-TLS на 853 и DNS-over-HTTPS на 443;
- пункт 11: ОС, ядро/архитектура, модель и число vCPU, наличие AES-инструкций,
  load average, RAM/Swap, свободный диск, IPv4/IPv6, виртуализация, TCP congestion control,
  qdisc, заполнение conntrack и синхронизация времени;
- `vmstat` в пункте 11: средний CPU steal за 5 секунд как признак времени CPU, которое
  гипервизор забрал у VPS из-за нагрузки соседей;
- OpenSSL в пункте 11: короткие трёхсекундные однопоточные AES-256-GCM и
  ChaCha20-Poly1305 benchmark — ориентир по криптографической мощности
  CPU, а не обещание реальной скорости Xray/WireGuard.
- короткая запись 256 MiB с `fsync` и чтение: грубая проверка проблемного диска, а не
  полноценная замена `fio`;
- три независимые IP-геобазы, ASN/владелец диапазона через RIPE RDAP, reverse DNS,
  hosting/datacenter/VPN/proxy/Tor/abuse-сигналы и Spamhaus DROP;
- фактическая доступность Google/YouTube/Play, Telegram, GitHub, ChatGPT, Gemini,
  Google AI Studio, Claude, Microsoft Copilot, Discord, Reddit, LinkedIn, Spotify,
  Netflix, Patreon, DigitalOcean, Snyk, MongoDB, Redis, Cloudflare и DNS-over-HTTPS;
- отдельный российский DPI-профиль: HTTP и HTTPS до целей из Censorcheck, включая
  YouTube/Google Video, Discord, Instagram, Facebook, X, LinkedIn, Rutracker,
  DigitalOcean, Amnezia, Outline, Mailfence, Telegram API и Google Play.

Диск не подвергается тяжёлому benchmark: для транзитной VPN-ноды он обычно не является
узким местом, а короткая запись нужна только для выявления совсем плохого хранилища.

## Проверка IP и блокировок

Отдельный запуск для текущего публичного IP:

```bash
python3 server_audit.py --tests ipinfo,access,dpi,dnscheck
```

Проверка заранее известного IP:

```bash
python3 server_audit.py --tests ipinfo --check-ip 203.0.113.20
```

`ipinfo` сравнивает `ipapi.is`, `ipwho.is` и `ipapi.co`, показывает расхождения страны и
города, ASN/организацию, PTR, данные владельца диапазона и reputation-флаги. Нахождение
обычного VPS в категории hosting/datacenter ожидаемо и не является дефектом.
Каждый VPN/proxy/Tor/abuse/bogon-флаг выводится вместе с названием сообщившей его базы:
одиночный флаг считается предупреждением, а не доказанным фактом. Повышенный риск
Tor/abuse/bogon ставится только при совпадении нескольких источников либо отдельном
попадании сети в Spamhaus DROP.

Для IP показывается отдельная оценка репутации от 0 до 100, а не общий балл всего
сервера. Например, если только `ipapi.is` одновременно сообщил `proxy` и `abuse`, а
остальные базы этого не подтвердили, вывод будет «условно подходит, нужно перепроверить».
Это предупреждение одного источника, не доказанный бан. Следующий полезный шаг — пункт
«Доступность популярных сайтов» и ручная проверка критичных для вас сервисов через этот IP.

Spamhaus DROP проверяется отдельно. Это список сетей, которые не рекомендуется маршрутизировать,
но не полный перечень почтовых DNSBL, антифрод-систем, локальных банов сайтов или записей
Роскомнадзора. Универсальной базы «заблокирован ли IP везде» не существует.

`access` не пытается угадать доступность по базе, а делает реальные HTTP- и HTTPS-запросы с
проверяемой машины. HTTP 403/451 отмечается отдельно, но 403 ещё не доказывает бан IP:
некоторые сайты блокируют автоматические клиенты или требуют cookie/JavaScript.
Табличный вывод показывает каждый сайт отдельно, его фактический IPv4 и раздельные
результаты HTTP/HTTPS. `HTTP 403` означает, что DNS, маршрут и TLS до сайта уже сработали,
но сайт отклонил конкретный автоматический запрос; полное отсутствие соединения является
более сильным предупреждением, хотя его всё равно стоит повторить из-за возможного тайм-аута.

Gemini проверяется автоматически в два этапа внутри `access`: отвечает ли
`gemini.google.com/app` и доступна ли Google AI Studio. Успешный ответ подтверждает DNS,
маршрут, TLS и то, что страница не отсекает IP на самом раннем этапе. Это не стопроцентный
тест «Gemini разблокирован»: Google учитывает страну, тип/возраст аккаунта и Workspace,
а полноценный запрос требует авторизации. Поэтому итог прямо предлагает один раз войти
через браузер с трафиком этого сервера и отправить тестовый запрос.

Пункт `DPI` повторяет полезную идею `vernette/censorcheck`: проверяет каждую цель по HTTP
и HTTPS и показывает результат отдельно. Массовые тайм-ауты на российском VPS являются
признаком фильтрации, но не доказательством DPI — так же могут выглядеть сломанный DNS,
маршрут, firewall или защита сайта. Скрипт намеренно не называет одиночный сбой «баном».

Пункт `DNS` проверяет системное разрешение имени, а затем Cloudflare, Google, Quad9 и
Yandex по UDP, TCP, DoT и DoH. Разные ответы CDN не считаются подменой: современный DNS
может законно отдавать разные адреса в зависимости от сети и географии.
У Quad9 DoH с конца 2025 года требуется HTTP/2, которого нет во встроенном HTTP-клиенте
Python; поэтому только эта ячейка честно выводится как «не проверено», а не как
«заблокировано». UDP/TCP/DoT Quad9 при этом проверяются полностью.

В `ipinfo` также показывается не только количество ответивших источников, но и отдельный
вывод `ipapi.is`, `ipwho.is`, `ipapi.co`, RIPE RDAP и Spamhaus DROP: страна, город,
ASN/организация, доступные репутационные флаги и источники каждого предупреждения.

## Что взято из multitest

Изученный `multitest` является меню, которое запускает сторонние скрипты: IP Region,
Censorcheck, российский `iperf3`, YABS, IP.Check.Place, bench.sh, IPQuality и sysbench.
В эту утилиту перенесены сами необходимые проверки без исполнения удалённого `curl|bash`:

- IP Region/IPQuality → несколько геобаз, RDAP, PTR и reputation-флаги;
- Censorcheck/IP.Check.Place → отдельные HTTP/HTTPS проверки сервисов и DPI-профиль;
- DNS Censorcheck → Cloudflare/Google/Quad9/Yandex по UDP, TCP, DoT и DoH без `dig`;
- russian-iperf3-servers → обновляемый каталог РФ, профили регионов и fallback портов;
- YABS/bench.sh → уже имеющиеся system/network/crypto тесты плюс осторожный disk I/O.

Автоматическое изменение BBR/qdisc и отключение IPv6 из раздела утилит `multitest` не
перенесены: диагностический скрипт не должен менять настройки проверяемого кандидата.
Geekbench/sysbench не включены в итоговый рейтинг: для VPN важнее измеренная скорость
AES/ChaCha под текущим CPU, steal time и реальная сеть.

## Оценка и её ограничения

Итоговая оценка — эвристика для первичного ранжирования, а не сертификат качества.
Порог скорости задаётся через `--expected-mbps`; сервер не штрафуется нулём за
пропущенный тест, но уверенность оценки снижается.

Используется один сбалансированный набор весов: задержка 30%, стабильность 25%,
пропускная способность 35%, система 10%. Path MTU в балл не входит. Потери на
промежуточном хопе MTR не следует считать проблемой, если последующие хопы и конечная
цель без потерь: маршрутизатор мог ограничить ответы ICMP.

Повторяйте полный тест минимум утром, вечером в часы пик и ночью. Для окончательного
выбора также отдельно проверьте:

- репутацию и блок-листы выданного IP, ASN и историю подсети;
- доступность нужных сайтов из этой страны/ASN;
- лимит трафика, цену перерасхода и политику провайдера по VPN/proxy;
- DDoS-защиту, порядок abuse-обращений и возможность быстро сменить IP;
- реальную производительность под вашим Xray/Remnawave-профилем и несколькими клиентами.

## Сравнение кандидатов

Скопируйте JSON-отчёты с VPS в одну папку и выполните:

```bash
python3 server_audit.py --compare reports/*.json
```

Сравнивать корректно только отчёты с одинаковыми целями, `iperf3`-точкой, ожидаемой
скоростью и примерно одинаковым временем суток.
